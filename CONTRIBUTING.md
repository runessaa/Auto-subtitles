# Правила работы команды

## Участники и ответственность

- [@runessaa](https://github.com/runessaa) отвечает за обработку медиа, распознавание речи и субтитры.
- [@PokachalovaKseniya](https://github.com/PokachalovaKseniya) отвечает за интерфейс Gradio, интеграцию и тестирование.
- Приоритеты и оценки согласуем вместе. У каждой задачи один исполнитель, второй участник проверяет результат.

## Ритм и связь

Спринт длится одну неделю. В начале - планирование на 15 минут; в конце - показ результатов и ретроспектива на 10 минут. Ежедневно оставляем короткий статус в issue: сделано, следующий шаг, препятствие. Обсуждения по задачам и окончательные решения сохраняем в GitHub Issues и pull requests. Даты встреч фиксируем при планировании.

## Бэклог

У задачи есть результат, исполнитель, критерии проверки, метка типа и оценка 1, 2, 3 или 5 очков. Очки показывают относительную сложность. Задачу на 8 очков и более делим. В первый спринт выбираем 3–5 задач; далее учитываем фактическую скорость команды. В зачёт идут только полностью завершённые задачи. Статусы в GitHub Projects.

## Ветки и коммиты

Перед работой обновляем main. Для каждой задачи создаём отдельную короткую ветку: `docs/N-description`, `feature/N-description` или `fix/N-description`, где N - настоящий номер issue. В main напрямую не работаем. Коммит содержит одно логическое изменение; сообщение описывает результат, например «Добавить описание пользовательских функций».

Не коммитим токены, пароли, веса моделей, личные медиаматериалы и временные результаты. Для демонстрации используем разрешённые тестовые данные и фиксируем их источник.

## Pull request и ревью

В PR указываем результат, способ проверки и `Closes #N`. Целевая ветка - main. Просим ревью другого участника. Ревьюер проверяет файлы и критерии задачи, затем выбирает Approve либо Request changes. Замечания исправляем в той же ветке. После одобрения и успешных доступных проверок сливаем PR и удаляем ветку. При конфликте учитываем обе правки, удаляем маркеры конфликта и повторяем проверку.

## Определение готовности

1. Все критерии приёмки issue выполнены, результат доступен по ссылке или в файле.
2. Проверка из issue выполнена; для нового поведения программы добавлены подходящие тесты и они проходят. Для документации проверены содержание, ссылки и отображение Markdown.
3. Другой участник проверил изменения и одобрил pull request.
4. Изменения слиты в main; секреты и случайные временные файлы не добавлены.
5. README и связанные документы приведены в соответствие с изменением, если оно на них влияет.
6. Issue закрыт, в Projects указан статус «Готово», ссылка на PR сохранена.

## Итоги спринта

Записываем число завершённых задач и сумму их очков. Незавершённые задачи переносим целиком. В ретроспективе фиксируем, что помогло, что мешало и одно изменение правил. Для версии с проверенным результатом оформляем релиз с описанием фактически доступных возможностей; документальный этап не называем готовым приложением.
